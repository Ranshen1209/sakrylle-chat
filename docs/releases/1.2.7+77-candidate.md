## 正式发布门槛与当前阻碍

本机未找到有效签名身份，GitHub 当前仅配置 Android 签名 secrets。macOS 现有构建只有 ad-hoc/linker 签名，不是 Developer ID 正式分发包。

正式构建需要安全配置：

- secrets：`MACOS_DEVELOPER_ID_P12_BASE64`、`MACOS_DEVELOPER_ID_P12_PASSWORD`、`MACOS_NOTARY_KEY_BASE64`。
- variables：`MACOS_SIGNING_IDENTITY`（Developer ID Application）、`MACOS_NOTARY_KEY_ID`、`MACOS_NOTARY_ISSUER`。

正式标签应为 `v1.2.7+77`，只能创建在验证通过的最终提交上。工作流验证标签/版本/SHA 并拒绝覆盖已有 Release；各 job 只收集到草稿。macOS 脚本完成签名、公证、装订和校验后才产出 DMG。未签名 iOS 仅供编译验证，不得加入正式发布。

尚需真正完成浏览器登录、安装/升级后的历史数据读取、桌面托盘/快捷键，以及 Windows/Linux/Android 的目标环境验证。没有将 macOS 编译通过视为其他平台通过。

## CI 后续安装验收修复

运行 `34762592465` 的 macOS arm64 与 iOS 无签名 Release 编译通过。Linux 编译成功后，Fedora RPM 安装暴露了随包 ONNX 库的 SONAME 与 ELF 版本基名不一致：消费者需要 `libonnxruntime.so(VERS_1.17.1)`，RPM 自动生成的版本化能力却使用 `libonnxruntime.so.1.17.1`。两个 Linux 工作流从实际导出的 `OrtGetApiBase` 符号生成缺失的能力别名，保留自动依赖检查，并增加安装后 ONNX API 与 Sherpa 动态库加载验收。没有更改应用代码或数据格式。
